# 复盘 #25 — v0.8.18 ZIP 内存错误提示与分批下载引导（2026-10-17）

> ↩ 复盘索引：[README](README.md)
>
> 当前状态：主站 v0.8.18 已发布到 Cloudflare 与阿里云；运营后台维持 v0.4.25、API 维持 v0.4.18。ZIP 打包发生浏览器内存分配失败时，用户会看到原因、优先替代路径和分批打包建议。

## 数据快照与实现边界

- 用户反馈点击“打包下载”后直接看到 `Array buffer allocation failed`。该文案来自浏览器在 JSZip `generateAsync` 阶段无法继续分配连续 `ArrayBuffer`，不是音频解密失败，也不是服务器错误。
- 当前 ZIP 实现需要在浏览器内同时保留已完成的音频 Blob、JSZip 中间数据和最终 ZIP Blob；文件数量与单曲大小都会推高峰值，因此“只减少歌曲数量”方向基本正确，但更准确的约束是减少每批音频文件的总大小。
- 本版识别 `Array buffer` / `ArrayBuffer` 分配失败、`out of memory` 与 `invalid typed array length`，显示“浏览器可用内存不足”，优先引导使用“下载全部”逐个下载；仍需 ZIP 时，提示清空列表后减少每批数量或总大小并分批打包。
- 未知 ZIP 异常不再直接暴露底层英文，统一提供逐个下载或减小批次的处理建议；原始异常仍写入既有 `ZIP_FAILED` 失败埋点，保留排障证据。
- 本版没有流式化 ZIP，也没有降低实际内存峰值；没有新按钮、新异步流程、新事件名、后台字段或 API 改动。

## 本次故障与根因

1. 用户可见错误的直接原因是 ZIP 生成阶段内存分配失败；现有实现的结构性原因是 JSZip `generateAsync` 需要在浏览器内生成完整归档，批量大文件时产生下一处显著内存峰值。
2. 第一轮 GitHub 设备授权被本机旧的无效凭据覆盖。明确登出该账号后重新授权成功；沙箱内不能读取 macOS 钥匙串，后续 GitHub 命令使用获批的系统权限读取凭据。
3. 本地 Git smart-HTTP 克隆仍未完成，发布继续采用 GitHub Git Data API，以远端 `main` 为基线创建单提交，并在 PR 前核对 ahead 1 与四文件差异。
4. Cloudflare 静态资源上传第一次出现瞬时失败，Wrangler 自动重试后 4/4 文件上传成功并返回正式 Worker 版本；没有留下半发布状态。
