# 复盘 #6 — 运营后台 v0.4.13 首页查询性能重构（2026-07-21）

> ↩ 复盘索引：[README](README.md)

## 问题与决策

生产 `events` 已约 240 万行、数据库约 1.37GB。旧首页把 overview、funnel、PV/UV 趋势、自定义趋势和设备拆成多个请求，其中 overview 内部又串行执行 21 次同步查询；90 天冷查询实测约 20–60 秒，并会阻塞同一 Node 主线程上的 `/api/track`。

本期保留 SQLite 和全部既有业务口径，不扩张访客、性能分析或日志页范围。方案分为两层：先用单 bundle、条件聚合、60 秒缓存和 Worker Thread 止血；再用精确日汇总、增量游标、文件终态表和可恢复回填根治长区间扫描。

## 发布前验证

- 后端专项测试 3/3：原始/汇总逐字段对账、自定义时间边界、文件状态优先级、批次恢复、缓存命中、并发合并、Worker 重启和 `raw_fallback`
- `npm run build:server`、`npm run build:admin` 通过
- 临时数据库回填覆盖今日、7/30/90/365 天和两个自定义区间，差异为 0
- 本地登录后切换 90 天、强制刷新、趋势/漏斗/设备交叉筛选正常；1280px 无横向溢出

## 上线步骤与观测

1. 合并代码后手动部署 API，确认健康检查和新 bundle 的 `data_source=raw`
2. 自动部署运营后台，确认版本号 `v0.4.13` 和首页只请求一次 bundle
3. 备份生产数据库，以 `building` 状态运行历史回填；对账成功后切换 `ready`
4. 记录 90 天冷查询、缓存查询、汇总延迟、`raw_fallback` 和 `/api/track` 健康度

首次生产回填的自动对账发现少量重复 `file_id`：旧接口按每条 `upload_attempt` 计数，初版文件终态表按唯一 `file_id` 计数，90 天成功数相差 140。`building` 状态正确阻止了错误汇总启用。修复为“file_id 终态 + 逐上传事件状态”双层派生表，并新增 `--reset` 只重建首页派生数据后再对账。

二次回填首轮对账差异为 0；同时暴露“持续有新事件时追尾直到完全静止”无法终止。修正为最多追尾一次并再次完整对账，第二次对账期间的新事件留给上线后的 30 秒增量任务，避免低流量要求变成启用前提。

上线前生产盘曾因日备份占满而 `SQLITE_FULL`：经项目主确认删除 2026-06-22 至 06-24 三份最旧备份，随后用 SQLite 在线 backup API 生成 `overview-v0.4.8-20260721.db`；源库和备份均 `quick_check=ok`。发布完成后磁盘剩余约 2.5GB。

| 指标 | 发布门槛 | 初始上线结果 |
|---|---:|---|
| 90 天 bundle p95 | ≤1.5 秒 | **0.99 秒**（5 次 0.65–0.99 秒） |
| 首页完整可见 p95 | ≤2 秒 | 未独立测量；公网 HTML 80ms，生产首页 bundle 0.76 秒 |
| 缓存命中 p95 | ≤300ms | **3.3ms**，最大 6.4ms（20 次） |
| 汇总延迟 p95 | ≤60 秒 | **0–1ms**；最终游标与 events 最大 id 一致 |
| 长查询期间 `/api/track` p95 | ≤100ms | **约 15ms**，最大 31ms；冷查询并发样本 3ms |
| `raw_fallback` | 稳定 24 小时后为 0 | 初始 smoke 为 0，24 小时窗口待补 |
| 新旧口径差异 | 0 | **0**；两轮七组生产区间自动对账通过 |

公网 `/admin/` 与 `/api/health` 均为 200，生产静态产物包含 `0.4.13`；汇总状态 `ready`、`last_error=null`、尾部事件为 0。因应用内浏览器连接生产站点超时，本次没有伪造“首页完整可见”指标，保留为后续真实 RUM/浏览器测量项。
